# Architecture - the module map

Split out of [ARCHITECTURE.md](../ARCHITECTURE.md). One row per file: what it owns, in plain
language, present tense. The terse version every session carries is in
[CLAUDE.md](../../CLAUDE.md)'s own module map; this is the one read on demand.

| File | What it does |
|------|--------------|
| `index.html` | The entry point and page markup, and nothing else. The JavaScript here is just wiring: grab the canvases, start PixiJS, call each module's `init`, connect the lifecycle events. The styling is nine `<link>` tags. It was once a ~2400-line script plus a ~1370-line stylesheet, and a guard hook keeps either from creeping back. |
| `src/css/*.css` | All of the app's styling, split by the part of the screen it dresses: `base.css` (page reset, the floating-panel surface every control shares, canvas layers, player mode), then `controlPanel.css`, `toolbar.css`, `roomCard.css`, `playerPane.css`, `legend.css`, `sceneManager.css`, `about.css`, `combat.css`, `overlays.css`. They load in that order and it matters, because CSS is one shared cascade. |
| `renderer.js` | The PixiJS/WebGL wrapper: the drawing context, the layers everything else hangs off, the map sprite and the texture pool behind it. Each fog pass has its own file beside this one. |
| `playerFogPass.js` | The Player's fog drawn as one pass over the whole window, shaders and all. Covering the window rather than the map is what leaves no edge for a seam to sit on. |
| `dmFogLayer.js` | The DM's fog, which is a different thing entirely: map-sized sprites, the crossfade between the fog before an edit and after it, and the drifting cloud texture masked to wherever fog is opaque. |
| `render.js` | The render loop. Each frame it decides which layers actually changed and redraws only those, keeps the canvases sized to the window, and paints the cursor and polygon-selection overlay. |
| `state.js` | Shared values that several files need. Loaded first so they exist before anything reads them. |
| `fog.js` | The fog itself: the canvases that store what is hidden, the blur pipeline that softens them, and the reveal/hide logic. |
| `fogAnim.js` | Four loops, each ticking against the clock: clouds drifting and morphing, a reveal or shroud fading in, the fog closing over a scene switch and opening again, and the fog colour easing from one scene's to the next. A loop that stalls shows the players a frozen picture, so each one owns its own frame handle and can be stopped on its own. |
| `fogClouds.js` | The soft moving texture that stops the fog reading as a flat fill. One window builds the sixteen frames and every other window copies them, because building four sets at once freezes all of them for seconds. |
| `fogControls.js` | Every control in the Fog tab: the animation presets and their sliders, and the colour, feather, half-shroud and door-size inputs. It reads and writes fog settings; it draws nothing. |
| `fogGeometry.js` | The pure fog math: polygon insetting, rounded paths, cone vertices, tint-colour derivation, animation timing. Plain functions in, values out, no drawing. Unit-tested. |
| `fogColor.js` | The colour arithmetic behind the fog: one picked colour into the solid fill and the tint that glows over it, the halfway step between two of them for a scene change, and the look settings a saved scene carries. Plain functions in, values out. Unit-tested. |
| `doorGeometry.js` | The pure door math: notch placement and corners, cell snapping, which wall a point is near, door placement from a floor plan, shared-wall detection, and the remap that keeps a door on its map point when the outline changes. Unit-tested. |
| `shapeDetail.js` | Carries a room's per-vertex and per-wall detail across a repair: it flattens each curve for the clipping library, then rebuilds the surviving stretches as exact cubics and puts each corner radius and each door back on the wall that now holds it. Unit-tested. |
| `vttPlan.js` | Turns a Universal VTT floor plan's wall segments into room polygons, and reports where its openings sit. Pure geometry, no dependencies, unit-tested. |
| `roomOps.js` | Reshapes rooms already on the map: joins the ones a drawn shape overlaps into one, trims a drawn shape out of them, and cuts one room into two along a clicked path. Wraps the vendored `polygon-clipping` library and answers with vertex lists or a refusal reason, never a throw. Unit-tested. |
| `floorPlan.js` | The app side of that: finding the plan beside the map, the offer notice, setting Grid Size from the plan at import, and drawing the rooms and their doorways. |
| `tools.js` | Which tool the DM is holding, the state every tool shares, and the table a click is dispatched through. Each tool is a row in that table and a file of its own, so a new one is added without touching the others. The cone is drawn apex-first - press at the point of origin, drag towards where it points - and commits as an ordinary polygon with a shallow arc on its far edge, so nothing downstream knows a cone from any other shape. |
| `shapeCommit.js` | What happens to a shape once it is drawn: it becomes a room, an effect, or a repair of one already there. Join, Trim and Cut all end here, and so does every refusal the DM sees. |
| `toolPoly.js` | The Polygon tool: one vertex per click, closing either by clicking the first vertex again or by crossing its own line. |
| `toolShapes.js` | The three tools drawn by dragging: rectangle, circle and cone. Each starts on the press and commits what it has on release. |
| `toolBrush.js` | The fog brush. Strokes queue while the pointer moves and land in one pass, so painting stays smooth on a big map. |
| `toolDoor.js` | The Door tool: which wall a click belongs to, where along it the door sits, and the notch that opens in the fog there. |
| `toolCut.js` | The Cut tool: a free path drawn across a shape, and the two pieces it leaves. |
| `shapeMarkers.js` | Draws one corner (square at object level, circle in edit mode, an optional coloured ring or stroke) and one hole's hatch fill. Read by shapeSelect.js, shapeBox.js and toolPreview.js alike, so it belongs to none of them. |
| `toolPreview.js` | The outline a tool shows while the DM is still drawing, before anything is committed. |
| `shapeHit.js` | What the cursor is over: whether a point is inside a room, how far it is from a wall, and where along that wall it lands. A bent wall is measured against its curve. Pure. |
| `shapeSelect.js` | The Select tool: what is picked, and every edit made by hand on the map. It holds the levels the way Figma does - one click picks a shape as a whole object and draws its bounding box, a double-click enters edit mode and puts its vertices, walls and holes in reach, and a Ctrl+click on a shape not yet open does the same in one press. A hole is picked by clicking its empty middle, takes a box of its own, and opens its corners on one more double-click; Escape climbs back one level per press. Only the live level answers the mouse. A hole moves as one ring and stops where it would leave its room. Also draws every room and effect: a wash carrying its fog state, a soft inner edge, and a line that goes gold when held and white while editing. |
| `shapeBox.js` | The bounding box a picked shape wears, and the rotate and scale its four corner handles drive. A corner scales against the opposite corner; the ring just outside it rotates around the box centre. Shift holds proportion and snaps rotation to 15 degrees. A picked hole gets the same box, and stops where it would leave its room. |
| `shapeClipboard.js` | Copy, cut, paste and duplicate for rooms, effects and holes, on Figma's Ctrl+C, Ctrl+X, Ctrl+V and Ctrl+D, and the copy an Alt+drag moves. Cut is a copy and a delete, one undo step; an Alt+drag makes its copy on the drag's first movement and spends only the drag's own undo step. A paste centres the shape on the pointer and a duplicate lands one grid square across. The copy keeps its name, its description and its fog state. The clipboard outlives a scene switch and remembers which list it came from, so an effect pasted in Rooms mode still lands among the effects. A copied hole pastes as a hole into whichever shape sits under the pointer. |
| `input.js` | The DM's mouse and keyboard: painting with the tools, keyboard shortcuts, the legend toggle. Files dropped on the window are `dragDrop.js`'s. |
| `undo.js` | Undo/redo history for fog edits. |
| `effects.js` | Map effects - burning ground, and the materials to come. Each is a polygon carrying a material name, drawn under the fog on both screens as a flaming border: the outline burns inward with dissolving tongues over a faint fill, with sparks, smoke and haze. Rendered by a fragment shader over the polygon's own distance field, in two PixiJS meshes per effect. Owns the `effects` array's model and the meshes that draw it; the passes themselves are `effectShader.js`'s and their colours `effectMaterials.js`'s. The look is a fixed set of numbers in the module with no UI over it. (The ember relight of the map grid inside a zone lives in `grid.js`.) |
| `effectMaterials.js` | What an effect is made of. A record per material carries the colours its fire burns through, how warm the hottest part reads, and the swatch the picker shows. A new material is a record here and nothing else. |
| `effectShader.js` | The two passes an effect is drawn with: one that adds light - flames, interior glow, sparks - and one over it that takes light away, for smoke and haze. Every colour arrives from the material. |
| `grid.js` | The grid overlay: squares or hexes, size/offset/colour, and line width that scales with zoom. Also the one place a grid change is committed from - redraw, push to the Player, save onto the scene - and what grid a freshly imported map starts with. Relights the grid in ember inside each effect zone (`drawEffectGridGlow`), because the map grid draws on a canvas above the effect layer. |
| `gridCalibrate.js` | Fitting the grid to a map that already has one drawn on it, without typing numbers. Armed from the icon beside Grid Reset, which shuts the panel and puts the room card away so the map is clear; leaving hands both back. **The DM drags the shape the grid is made of.** For a square grid that is a box from one intersection in the map art to another several cells away, forced square because a cell is, which makes the two axes one measurement and lets a map showing only its vertical lines be enough. For a hex grid it is one big hex dragged from a corner to the opposite corner, snapped to one of the six corner directions because corners are what the map art draws, with the grid's hexes drawn inside it. Its diagonal crosses n hexes, each twice the circumradius with a shared wall of one between neighbours, so it is (3n - 1) circumradii; an odd n centres the big hex on a cell and lands all six corners on the grid, and an even one lands only the two corners pressed. The DM's grid is hidden for the length of the gesture, and the square and the big hex each draw their own cells. The cell count is guessed from the size already set and corrected with a stepper floating beside the shape, so the cell is the drag divided by what that count spans; the stepper sits clear of the magnifier; a drag too small to fit one cell is refused rather than clamped. Once drawn the shape stays live: drag its middle to slide the phase with the cell size held, or its far handle to resize with the count held. Past the box, a square grid also offers a handle on any intersection that re-solves the cell size by least squares so the grid lands there, which takes out the error a short measurement multiplies over a long map. A magnifier shows the map at four times the on-screen scale, and an animated map is held on one frame for the length of the gesture. Owlbear Rodeo, Roll20 and Foundry all size from a fixed multi-cell square and then correct at a distance; this is that shape with a count the DM can raise. |
| `scenes.js` | Auto-save loop, fog-load helpers, and the error-recovery path above the database layer. |
| `sceneCards.js` | What a scene looks like in the library: the card, its thumbnail, its editable name, the group heading it sits under, and the dragging that moves it between them. A drag reads both facts back out of the page at once - which section a card ended in, and the order across all of them. |
| `sceneDelete.js` | Deleting a scene, and taking it back. The list loses the scene at once, but the database keeps it until the undo toast runs out, so the DM can undo a mistake mid-session. Deleting the scene on screen also empties the app and moves it to another one. |
| `sceneManager.js` | Scene CRUD and the scene library: rename, delete, thumbnails, order and groups. The library is a popup over the map, with a find field, group headings you drag cards into, and a contextual bar that replaces the header while anything is selected. |
| `mapImport.js` | Turning files the DM picks or drops into scenes: which kinds are accepted, how a whole selection is taken in one at a time, how a second import waits for the first to finish, and where an animated map is written. Problems are collected and reported once at the end, so a long import never waits on a click. |
| `sceneSwitch.js` | `switchScene`: the fog closing over the outgoing map, the store read, the decode, and the fog reopening on the new one. Every path into a loaded map goes through it. |
| `sceneGroups.js` | Groups in the scene library. A group is a name a scene carries, so the scene's own `group` field is the only record of what is filed where; this file keeps the order the headings appear in, which ones are collapsed, and a heading made before anything was dragged into it. |
| `sceneStore.js` | Saving and loading scenes to the browser's local database (IndexedDB). Changing one field of a scene the app is not currently showing goes through `updateScene`, which reads and writes in one transaction so an autosave cannot land between the two and lose a fog reveal. |
| `mapLoader.js` | Loading a map image into the app and driving the progress bar, including the batch label a multi-map import puts on it. Shared by scene-switching and backup restore. |
| `mapConvert.js` | Asking whether to shrink an oversized animated map at import, and re-encoding it if the answer is yes. Pure box-fitting maths plus the recorder that drives it. |
| `viewport.js` | Pan, zoom, fitting a map to the screen, and the camera arithmetic every push to the Player carries. |
| `playerWindow.js` | The DM's side of the Player window: opening it, keeping a warm one ready so the next press is instant, and deciding what is sent to it and when. |
| `minimap.js` | The DM's live preview of the Player camera, and the remote control that drives it. |
| `stageWindow.js` | The DM side of the Player screen while two maps are up: opening that window, keeping a warm one ready so the next press is instant, wiring each column to its own half, and closing it. |
| `paneRuntime.js` | The other end of every command the DM shell sends a column. Each message presses the control that column already has, so a column behaves like the DM window it is, and no behaviour is written twice. |
| `panes.js` | Two-column mode, where the DM window's map area splits in two and each half holds a whole second copy of the app running in an `<iframe>` with its chrome hidden. Owns the two frames, which column is selected, the draggable divider, and every command the DM's chrome sends into a column. A column therefore has its own scene, camera, grid, rooms, fog, undo history and Player window with nothing written for it. Also the small piece that runs INSIDE a column: Electron gives a subframe no bridge to the shell, so the column borrows the parent window's. |
| `stage.js` | The Player window in two-map mode. One window, split where the DM's divider sits, holding a whole Player in each half and painting the chasm between them - a dark band with each floor's fog colour bleeding in, embers drifting up it and a faint seam of light down its centre. One window rather than two because Windows gives one fullscreen window per display, so a pair could never both be fullscreen on the same TV. |
| `video.js` | Animated (video) map support: file loading, DOM compositing, decoding, the frame loop, the freeze watchdog. |
| `videoDiag.js` | A panel that shows how an animated map is actually playing, plus the log file it writes. The counting runs whether or not the panel is open, so a stutter the DM only hears about later is still on record. |
| `display.js` | Detecting the Player screen's real size so the fog and map render at the right resolution. |
| `backup.js` | The export/restore-to-zip feature. |
| `dragDrop.js` | What happens when files are dropped on the DM window. Maps become scenes through the ordinary import; a floor plan arriving alone is attached to whatever scene is open, which is the case where it got separated from the map it belongs to. |
| `toolbar.js` | DM-only UI control wiring: toolbar buttons, sliders, the scene dropdown, Player controls. The Fog tab's own controls live in `fogControls.js`. Also the Rooms/Effects switch, the Merge and Cut out repairs, the material picker, and which tools each mode puts on the bar. The strip above the toolbar changes with both - `input.js`'s `updateContextPanels` owns every visibility decision in it. |
| `shapeMenu.js` | The single shape button on the bar and the flyout its right click opens. Keeps the button wearing whichever of Rectangle, Circle, Polygon and Cone the current mode last drew with. |
| `colorPicker.js` | The fog colour control: a saturation square, a hue strip and a hex field, kept in step with each other. It writes into the same hidden colour input the rest of the app listens to. |
| `controlPanel.js` | The Fog/Grid/Player control panel and the tab bar above it. A presentational layer over the older hidden controls. The tab bar sits outside the panel and never hides; picking a tab opens the panel on that pane, picking the same tab again shuts it, and the open pane is remembered between sittings. |
| `roomPanel.js` | The names drawn on the DM's map over each room, and the arithmetic that finds a spot inside the shape where a name fits. |
| `roomCard.js` | The small panel that appears beside a selected room, holding its name, notes, fog state and corner rounding. It keeps clear of the room it belongs to, and the DM can drag it anywhere. |
| `moduleText.js` | Parsing a published module's text into locations, storing them, and carrying them through a backup. |
| `moduleTextPanel.js` | The panel that takes a module file, and the room name field as a searchable dropdown over what it found. |
| `pdfLayout.js` | Turning a PDF's scattered text fragments back into reading order. Pure functions, unit-tested, no dependencies. |
| `pdfExtract.js` | Runs pdf.js in an isolated child process. No `<script>` tag: this one never loads in the browser. |
| `confirmDialog.js` | The app's own dialogs: a yes/no question, and a one-button message for errors. The only sanctioned pair, because a native `confirm()` or `alert()` breaks the page's focus. One shows at a time; a second waits its turn rather than replacing it, so no question is dropped unanswered. |
| `about.js` | The About block: the app mark, the version number and the repo address. Builds its own markup rather than adding any to `index.html`, and fills the shortcut legend's footer, so one button opens both. DM only. |
| `musicPlan.js` | The music library's pure kernel: it reads a pasted YouTube link into a video or playlist id, reads a track's id and display name back out of its filename, filters the track list, and gives the equal-power level of a fade at a given phase, and says whether the bundled downloader is older than the newest release. No DOM and no Electron, so it is unit-tested. |
| `music.js` | The music bubble at the top of the DM window: it lists whatever audio files sit in the app's music folder, plays one on a click and crossfades to the next, pauses without losing its position, carries the volume and the filter, deletes a track, and and opens the Add music panel. The folder is the whole library, so there is no database behind it. DM only. |
| `musicDownload.js` | The Add music panel: it reads a pasted YouTube video or playlist link as it is pasted, lists what is behind it with the tracks already on disk marked, and downloads the ones ticked one at a time. How far a queue has got is drawn as a hairline across the bottom of the music pill, which is the one control always on screen, and a queue still running survives the panel being closed and reopened. It also carries the button that updates the downloader, which appears only when a newer release of it exists. Split out of `music.js` and joined to it by three functions rather than a shared variable. DM only. |
| `combatPlan.js` | The arithmetic behind the fight table: adding up the HP line the DM types after the stat block's max HP, whether a creature is bloodied or down, initiative order, ability modifiers. Also the copy of a bestiary entry a picked row takes, the name a repeat gets, and merging a backup. Plain functions, unit-tested. |
| `bestiaryPlan.js` | The bestiary's rules: the size, type, alignment and movement a monster is filed under in either language, which monsters a search and the filters let through and how many each option would show, their order, a save's value, and the file an export writes and an import reads. Plain functions, unit-tested. |
| `combatTracker.js` | The fight table on the DM's screen: one fight for the whole app, a row per creature with initiative, name, HP, AC and conditions, rows dragged into any order, and the button beside Two maps that opens it. The fight is saved as it changes and goes into backups. Nothing in it reaches the Player. |
| `combatStatBlock.js` | The stat block that opens beside the fight table, laid out like a printed one and editable in place, and the same editor the bestiary's Edit uses. From the fight table it edits that row's own copy, which reaches the bestiary only through Save to Bestiary. |
| `statBlockParse.js` | Reads stat block text, English or Russian, into the fields the stat block popup shows: the labelled lines, the six scores, and each named entry under its section. On a web page it finds the block by its AC line and ends it where the page's own box around the block closes, so any site works with no reader of its own. A description on the page is kept as the monster's lore. Plain functions, unit-tested against pages saved from several sites. |
| `statBlockImport.js` | Turns pasted monster links into new bestiary entries, one after another in a queue the bestiary shows: reading, failed with the reason, or done. Each entry is sourced to the site it came from and numbered when the same name and source are already there. It never replaces an entry. |
| `bestiary.js` | The bestiary: every stat block the DM keeps, in a large window opened by the Bestiary button. A table sorted by any column, a name search and filters for size, type, challenge, source, alignment and movement, several picked at once to duplicate, export or delete, and imports from links or a file. A click opens the monster's page beside the table. |
| `bestiaryPage.js` | A bestiary monster's page in one column: AC and HP large, Initiative and Speed under them, six ability cards, then its traits, actions, lore and the DM's own notes. It reads until Edit, which swaps in the stat block editor. |
| `changelogData.js` | Every release the app has had: version, date, the line that headed its notes, the description under it, and its tag where it was released. Generated from the release commits by `tools/build-changelog.js`, so the list in the app and the notes on GitHub are the same text. |
| `changelog.js` | The What's new panel: the release list in a scrollable card, with the installed version marked. A release opens to the full note it shipped with, and to a button that opens its page on GitHub where one exists. Opens from the About footer and from the toast that follows an update. DM only. |
| `updater.js` | What the DM sees about updates: a toast in the top right when a download is ready to install, and the line under the About block that says what the download is doing. After a restart into a new version, the toast says so and offers the What's new panel. Reports only what the main process tells it, and shows nothing at all when there is no update or when the check failed. Where the app cannot replace itself, it offers the releases page instead. DM only. |
| `player.js` | Player-mode runtime: the card shown while the first map decodes, the handshake with the DM, the resize listener, and the players' own pan and zoom. |
| `playerMessages.js` | Everything the DM can say to a Player window, and what each sentence does when it arrives. |
| `playerMap.js` | A new map arriving on the Player: holding the screen dark until both the map and its fog have decoded, then swapping in an image or a video and easing the fog back off. The players must never see a half-applied scene, which is what most of the care here is for. |
| `stress.js` | A hidden stress-test harness for chasing video and memory bugs. Dormant unless the page is opened with `?stress=1`. |
| `memProbe.js` | A hidden memory probe: counts what one loaded map costs and writes it to the diagnostics log. Dormant unless the page is opened with `?memprobe=1`. |
| `main.js` / `preload.js` | The Electron shell. Creates the windows, tells both of them which screen the Player is on, and hands every subject below the folders it writes into. `preload.js` is the bridge the page talks to. |
| `electron/videoFiles.js` | An animated map's own file on disk: written as it imports, read back for the Player to play its own copy, listed for the memory probe, deleted with its scene. |
| `electron/music.js` | The music folder, which is the whole library - no database. What is in it, what a pasted link resolves to, and the downloader that fills it. |
| `electron/floorPlan.js` | Looks beside a map on disk for the `.dd2vtt` that came with it. |
| `electron/diagLog.js` | The playback log every window writes into, rotated on each start, with a few past runs kept. |
| `electron/updates.js` | Asks whether a newer release exists, downloads it, and holds the state the About line and the toast read. |
| `electron/pdfText.js` | Runs a campaign PDF through the parser in a separate process, so a malformed file cannot take the app down. |
| `electron/backupZip.js` | What goes into a backup zip and what comes back out of one. |
| `electron/statBlockFetch.js` | Opens a monster page in a hidden window, lets the site's own scripts draw the stat block, and hands back the finished page. Any web address; never a file on disk. The window is never shown. |
